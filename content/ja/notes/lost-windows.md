ウィンドウが消えます。Alt-Tab で戻らず、タスクバーにも居ない。プロセスは
生きています。

GlazeWM は非アクティブなワークスペースのウィンドウを画面外へ動かしません。
DWM の cloak で隠します。cloak されたウィンドウは合成から外れるだけで、ほかは
全部そのままです。可視で、画面内の矩形を持ち、最小化もされていない。z オーダーを
上げても何も起きません。隠しているのが z オーダーではないからです。

GlazeWM を再起動すると、シェルが報告するウィンドウを列挙します。cloak された
ウィンドウも報告されますが、直前まで誰かが管理していたという情報は付いてきません。
マネージャだけが居なくなり、cloak は残ります。

## 誰も好きで再起動しない

意図的な再起動はむしろ稀なほうです。実際に迷子を作っているのはこの 3 つ:

- GlazeWM がクラッシュして立ち上がり直す。
- モニターを挿す、あるいは外す。
- プレゼンテーションモードを on / off する。

後ろの 2 つは中身が同じです。ディスプレイ構成が変わると、GlazeWM はモニターと
ワークスペースの構成を組み直します。組み直す材料はシェルの報告で、そこでの cloak
は「今こうなっている」という状態でしかなく、誰が付けたかは残っていません。

見ていないワークスペースへウィンドウを送る仕掛けは、どれもこれを太らせます。
送られた先で即 cloak されるからです。起動時にアプリを所定のワークスペースへ
片付ける `window_rules` が、たいていの出どころです。

## cloak を外せるのは持ち主だけ

別プロセスから `DwmSetWindowAttribute(DWMWA_CLOAK, 0)` を呼ぶと
`E_ACCESSDENIED` が返ります。権限の問題ではありません。GlazeWM 自身も同じ
ユーザーの非昇格プロセスで、cloak には未文書のシェル COM 経由で触れていて、
その vtable レイアウトは Windows のビルドごとに動きます。つまり汎用の復帰手段は
無く、戻り道はアプリが用意している場合にだけあります。

wezterm には用意があります。GUI プロセスごとに
`~/.local/share/wezterm/gui-sock-<pid>` へ制御ソケットを開いていて、
`WEZTERM_UNIX_SOCKET` をそこへ向ければ `wezterm cli` はそのプロセスと話します。
ペインを新しいウィンドウへ移すよう頼めば、ウィンドウを作るのは wezterm 自身です。
今このタイミングで作られたウィンドウに cloak は付いていません。

`glazewm/rescue-window.ps1` は、そのプロセスが持つペインを全部集めます。cloak
されていないウィンドウに既に居たペインも含めて、まとめて新しいほうへ移します。
それ以外のアプリについては分かっていることを出すだけです。アプリを再起動するか、
`explorer.exe` を再起動してシェル側の cloak を全ウィンドウ分リセットするか。

## 「管理されていない」は 3 種類ある

難しいのは復帰よりも一覧のほうです。「GlazeWM が管理していない」は、壊れた
状態と、正常な状態 2 つを同時に指します。

| | cloak | immersive | |
|---|---|---|---|
| 迷子 | > 0 | いいえ | マネージャを失い、どこにも描かれない |
| 未管理だが描画済み | 0 | — | `config.yaml` の `ignore` ルール |
| サスペンド中の UWP | > 0 | はい | シェルの仕業で GlazeWM ではない |

ignore ルールが未管理のウィンドウを作るのは意図どおりで、UWP を cloak するのは
シェルの仕事です。どちらも迷子として出せば、本当に見るべき 1 件が、見なくていい
十数件に埋もれます。

1 行目と 3 行目を分けているのが `IsImmersiveProcess` です。今まさに管理されて
いるハンドルは `glazewm query windows` が返し、全体からそれを引きます。残りは
`EnumWindows` を、タイトルを持つトップレベルのうち最小化でもツールウィンドウ
でもないものへ絞ったものです。

## 既定は一覧

スイッチ無しで走らせると一覧を出します。復帰には `-Rescue` が要り、一覧が長い
ときのためにプロセスやハンドルでの絞り込みもあります。自分の判断でペインを
勝手に動かすツールは、元の問題より厄介です。
