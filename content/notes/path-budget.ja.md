`cmd.exe` が環境変数を展開できるのは 8,191 文字までです。`PATH` がそれより
長くなると、cmd は切り詰めて警告するのではなく、`PATH` からコマンドを探すこと
自体をやめてしまい、あらゆるコマンドが次のエラーで失敗します:

```
'x' is not recognized as an internal or external command
```

これはインストールされていないプログラムを呼んだときと同じメッセージなので
誤解しやすいのですが、実行ファイルはディスクにあり、cmd はそれを探して
いません。

## PowerShell を使っているマシンでも cmd が関係する理由

`cmd` を対話的に開くことはありませんが、ふつうの作業の中で cmd は動いています:

- npm と pnpm はパッケージスクリプトを `cmd` 経由で実行します。
- Node の `child_process` は既定で `cmd` を使います。
- この 2 つから起動されるものも同じ挙動を引き継ぎます。

そのため、ターミナルから実行すれば通るビルドが、パッケージスクリプトの中では
`PATH` の長さだけを理由に失敗することがあります。

## 何が文字数を使っているか

問題になるのは、レジストリに保存されている常設の `PATH` の長さではありません。
mise はツールを実行するとき、管理しているすべてのツールの bin ディレクトリを
先頭に足してから実行します。この展開後の `PATH` が 8,191 文字に収まる必要が
あります。

[このマシン](/ja/machine/)で 2026-08-04 に測った値です:

| | |
|---|---|
| 常設の `PATH` | 2,932 文字、60 エントリ |
| mise の shim から見た `PATH` | 7,392 文字 |
| mise が足した分 | 4,460 文字 |
| 上限までの残り | 799 文字 |

常設分は全体の 5 分の 2 ほどで、残りは mise の分です。mise の分はツールを足す
たびに増えます。手で書いているのは常設分だけなので、短く保てるのもそこだけ
です。

## 削る価値があるもの

常設の `PATH` からエントリを 1 つ削ると、その文字数がそのまま余裕に戻ります。
削る価値があるのは、実際には使われていないエントリです。そのディレクトリの
コマンドがすべて、`PATH` の前方にある mise の shim で提供されている場合や、
ツールが mise 管理に移ったあとも古いディレクトリが残っている場合がそれに
当たります。こうしたエントリは長さを消費するだけで、何も解決しません。

エントリの順序の規則は `windows/path-order.toml` に書いてあり、
`windows/doctor.ps1` が実行のたびに、その順序と残りの余裕の両方を検査します。

## 残りはどれくらいか

799 文字は、ツールのディレクトリにしておよそ 8 つ分です。余裕がなくなると、
最初の兆候はパッケージスクリプトが `node` を見つけられなくなることです。
